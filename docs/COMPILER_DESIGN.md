# Compiler design and demand coverage

This is an implementation review against [the 81-case demand catalogue](COMPILER_API_DEMAND.md), not an acceptance report for those cases. The current package supplies a general proof-authoring foundation. **Whether real Agents retain nomf-level reformulation quality and comparable time while completing verification remains pending.** Encoding a historical certificate or passing small examples does not establish that result.

The usage contract and examples are in [COMPILER_API.md](COMPILER_API.md). Counts below are demand occurrences from catalogue §3, not numbers of cases passed by this implementation.

## Architecture and responsibility

The path is Python `Model` / `Expr` / proof handles → existing typed `Certificate` → existing RPX encoder → Kernel verification. `compile` reads structured Certificate JSON directly; it does not call the RPA assembler. Compilation prepares an encodable object. Only verification against the complete caller Request and actual model pair establishes the requested relation.

The author chooses the reformulation, proof, domain, observations, and recovery maps. The compiler supplies exact sparse arithmetic, named references, scoped proof handles, explicit model edits, and Kernel-owned obligation enumeration. It automatically reuses identical facts and tautologies. Selected pivot cancellation, supplied row combinations, and fixed-coordinate equalities are deterministic elaborations of supplied evidence. It does not discover aliases, choose a dominance transformation, search combinations, enumerate a refutation, or find a feasible witness.

Kernel preparation owns generated model scopes for interval, menu, signed, flow, subflow, restricted-domain, and paired injectivity constructions. Preparation exposes the exact model and required old-scope premises; it accepts no premise as proven. The verifier repeats the checked construction and validates every premise in its original scope. Return planning uses the verifier's own obligation walk, including bounds, rows, integrality, objective gaps, observations, and applicable compositions. Python never maintains a separate guessed obligation order.

## The complex families still require proof work

The catalogue's sharpest cases explain why a general builder alone is insufficient evidence of usability:

- **Recovery and constructive bijections** (test13, test28, test59–test63, test72): the API prepares exact extension and paired domains and enumerates recovery/composition obligations. Generated coordinates and rows are exposed as lists plus the actual Model. There are no semantic per-menu-option, per-arc, or per-signed-component recovery handles yet. Multi-instance authors may still need to interpret the frozen layout to select the right generated handle.
- **Dominance, exchange, and logical aggregation** (test24, test47, test51, test87): complete piecewise maps and supplied Cases/linear proofs can express the existing certificates. No packaged dominance or exchange proof template has yet replaced their specialized preparers. Small binary-strengthening tests do not validate these larger workflows.
- **Large elimination and homogeneous cut families** (test10, test16, test42, test57, test70, test74, test83): sparse accumulation and source-fact lookup avoid copying a whole coefficient map per linear premise. Same-model branches reuse base indexing; dropped local facts no longer shadow live alternatives. Whole model/plan/certificate materialization and repeated expanded checks remain major costs to measure on real cases.
- **Parity and bounded refutations** (test67, test84): an author can supply explicit case trees and exact existing-rule derivations. There is no parity-fixing template or bounded search engine. Automatic search is outside the requested compiler scope; deterministic elaboration of an author-provided parity/refutation witness could be added if Agent feedback shows a need.
- **Fixed-coordinate equality closure** (test23): `eq_on_fixed` covers explicitly supplied one-coordinate equality facts and variables fixed by their model bounds. More general affine definitions can be combined with `rewrite` / `combine_rows`; the compiler does not discover a closure.

`compile_certificate` exposes every frozen Certificate variant as a structured Python object fallback. This prevents a convenience wrapper from excluding an existing wire feature. It does **not** establish natural proof authoring, comparable time, or unrestricted mathematical expressivity: all supplied proofs must still fit the frozen Kernel rules and limits.

## Resource and delivery boundaries

Direct compilation removes the RPA intermediate and its separate text policy. It retains the Certificate JSON parser's nesting bound and size policy, RPX item/depth/byte bounds, and verifier work/live-fact limits. Python and Rust currently hold complete structures in memory. Avoid extrapolating the small-test timings to the catalogue's hundred-megabyte certificates or claiming that every historical resource failure disappears.

`compile_certificate(..., committed_model=...)` loads the actual submitted artifact through the Kernel and requires `Model.same_formulation` with the verified target; it records the submitted artifact's hash as well. The comparison retains named variables/rows, bounds, integrality, objective, and coefficients, while allowing model NAME/order differences and exact folding of row constants into RHS values. `verify_bundle` rechecks artifact digests and this formulation binding. The real-run harness also anchors the source in the run's actual input and independently replays every RPX piece. Bundle coverage and any ancillary report assertions still need explicit review: verifying all listed pieces does not establish that the inventory captures every intended property.

## Validation status and acceptance gate

The current Python suite exercises exact model roundtrips, edits, ranged facts, affine inverse proofs, integer rounding, local cases, interval recovery, constructive injectivity/compositions, strict improvement, restricted levels, point exclusion, and scope/drop/precondition failures. These tests demonstrate selected mechanical invariants and verified example proofs. They are not 81-case Agent acceptance evidence. Tests are in [python/tests](../python/tests/); Rust bridge/planner tests are in [crates/core/tests](../crates/core/tests/).

`python/pyproject.toml` declares Python **>=3.9**, uses setuptools >=61 as its build dependency, and adds no runtime dependency. Imports and the full current Python test suite have been exercised with the host's Python 3.9.6. Build-tool availability is separate: the host's installed setuptools 58 does not satisfy the isolated-build requirement; normal isolated package installation must obtain the declared build dependency. Checkout use through `PYTHONPATH=python` requires no package build.

Real-run acceptance remains open. Use previously tested `reform_test` cases with the same model, Agent, solver access, prompt constraints, and budgets as nomf. Preserve unrestricted reformulation exploration; allow the Agent to report tool gaps. Record target/model quality, wall time, proof-authoring/tool time, all requested relations, verifier outcomes, and complete artifact identity. Include materially different proof families and demanding cases rather than accepting only the easy reductions. Feedback should drive compiler changes without weakening the chosen target or intended theorem. Acceptance requires demonstrated reformulation quality close to nomf together with autonomous complete verification and comparable overall time.
