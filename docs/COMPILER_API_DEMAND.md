# Compiler API demand: what the 81 reformulation cases need

Status: **analysis document, not a format or ABI specification.** It records what the
delivered corpus and the underlying agent trajectories demand from the compiler layer that
will sit on top of the RPX kernel, and it proposes an API shape. Nothing here changes a
wire format, a rule, a status or a resource limit. The kernel contracts it discusses, including V9 objective-level input domains
and V10 strict improvement / image exclusion / affine input restrictions, are frozen
as of 2026-10-14; see [FORMAT.md](FORMAT.md). Compiler APIs proposed here remain
analysis. Historical path/line citations below refer to the source snapshot at
commit `1468f95`, before the format consolidation.

Scope: cases `test8` … `test88` (81 cases). Every case has one row in §3 and one entry in §6.

## 1. Method and evidence

Each case was analysed from three independent evidence sources, never from the case's own
README alone:

| source | what it proves | where |
|---|---|---|
| the domain agent's trajectory | what the reformulation mathematically required, and what the agent had to do by hand | `reform_test/runs/<case>-nomf-B1/session.jsonl` plus `output/report.md`, `output/verify.py`, `output/audit.json`; `test8`/`test9` use a root-level session export |
| the delivered kernel case | what the certificate actually has to encode, how big it is, which limit binds | `cases/<case>/README.md`, `preparation.json`, `request.json`, `proof.rpa`, `proof.rpx` |
| the case's own generator | today's compiler, in the only form that exists | `tools/prepare_<case>*.py` and the sibling preparers it imports |

The trajectory was condensed for reading with a small tool, so a per-case reader does not
have to load a raw session:

```sh
python3 tools/digest_reform_run.py test36 --out /tmp/digests/test36.md   # report verbatim + bounded transcript
```

The digest keeps the agent's final report unchanged, caps commentary, keeps every `eval`
snippet it wrote (the Python/mipframe work), keeps failing tool results, and reports the
evaluation row (turns, tool calls, failures, tokens, wall time). Each case then received one
independent analyst whose only job was to answer: *which API capabilities does the compiler
need so that proving this case is natural and efficient, and what should they look like?*
Answers were required to cite `path:line` evidence and to rank at most six capabilities on a
fixed vocabulary, so the 81 answers can be aggregated. The per-case answers are in §6; the
aggregate is §3–§5. Claims in this document that are not attributed to a case come from the
kernel tree itself and are reproducible with the command shown.

Evidence rules applied throughout: no claim about a case without a traceable source; a
capability that cannot be tied to a case's evidence is not listed; `[UNKNOWN]` marks a gap
rather than a guess.

## 2. Where the compiler stands today

The kernel is a verifier with a CLI, a Rust façade and public proof data types,
but **no high-level proof-synthesis or compiler builder API**:

- CLI (`crates/core/src/main.rs`): `canonical`, `assemble`, `disassemble`, `inspect-model`,
  `export-model`, `verify`. Statuses and exit codes are documented in `docs/API.md`.
- Rust façade (`crates/core/src/api.rs`, `pub mod api`): `canonicalize_path`,
  `assemble_paths`, `disassemble_paths`, `inspect_model_path`, `export_model_paths`,
  `verify_paths`, `verify_bytes`, `read_input`/`read_text`/`write_output`, `Error`, `Status`,
  `Timings`, `limits_json`, and `model::to_json` for canonical model JSON.
- Lower-level `model`, `proof`, `codec`, `rpa`, `verify` and the static extension
  modules are public. A Rust caller can construct Certificate/Request values,
  encode RPX directly and call the verifier without RPA text. Public extension
  preparation functions generate candidate models and unchecked premises; they
  neither synthesize proofs of those premises nor authorize acceptance.
- `build_support` remains private (`crates/core/src/lib.rs`: `mod build_support;`).
  Untrusted proof-authoring helpers live in Python preparers and tests. The typed
  compiler builders, automatic obligation planning and proof synthesis proposed
  below are not an implemented API.

The corpus authoring workflow measured for this analysis consists of
**90 hand-written Python generators**
(`tools/prepare_*.py`), one per case plus a few shared experiments:

| measure | value |
|---|---:|
| generator files | 90 |
| total generator lines | 12,731 (median 126, largest `prepare_test72.py` 443, smallest `prepare_test85.py` 5) |
| distinct helper names defined across them | 192 (385 definitions) |
| generators that import a sibling generator | 86 of 90 |
| `rpx` subprocess mentions inside generators | `canonical` 142, `assemble` 101, `verify` 97 |

Those shell-outs matter: the generators call the CLI instead of a library, and every one of
them re-implements a slice of the same six helpers. The most-imported modules are the de-facto
API this corpus has:

| module | importers | what it provides |
|---|---:|---|
| `tools/prepare_affine.py` | 80 | MPS parsing with exact `Fraction` coefficients, row references |
| `tools/prepare_test40.py` | 77 | affine expression construction and RPA JSON (`expression`, `plus`, `mul`, `expr_json`, `row_fact`, `substitute`, `sha`) |
| `tools/prepare_test70.py` | 34 | `SparseBuilder` — the working builder object |
| `tools/prepare_test88.py` | 32 | `Builder` — a second, overlapping builder object |
| `tools/prepare_test57.py` | 32 | `substitute` — the affine-substitution edit |
| `tools/prepare_test54.py` | 25 | `fact`, `box`, `exact` — witness selection for an obligation |

So the demand in §3–§5 is not hypothetical: it is what those 12,731 lines and 385 definitions
are standing in for, measured case by case.

## 5. What the API should look like

The 81 analyses agree on one diagnosis: **the mathematics is settled long before the proof is
written.** The domain agent already discovers the edit, proves it in prose and checks it with
its own parser; what costs the compiler effort is re-stating that discovery in a form the
kernel will accept. Three things are re-derived by hand in every single case, and every
proposed capability below exists to remove one of them:

1. **The edit** — `target = source + edits` is never a kernel-visible fact. It lives in the
   analysis agent's `audit.json` (an untrusted, per-case schema the preparer reads by hand:
   test20, test43, test52, test59 all describe this), and the only binding is a hash in
   `preparation.json` (test20) or a full hand-written re-diff (test37's
   `independent_full_target`, `tools/prepare_test37.py:55-89`).
2. **The obligation list and its order** — the checker owns it (`crates/core/src/verify.rs`'s
   obligation order is reproduced by hand in `Git 1468f95:docs/CURRENT_FORMAT.md:226-238`; test26 calls it
   "kernel-owned, generated from the output model"), yet the caller must write exactly one
   witness per obligation in that order. Measured on the shipped artifacts: identity maps plus
   per-coordinate obligation lists are 67.0% of test16's 109.7 MiB certificate (maps 28.8%,
   checks 38.2%, steps 22.7%, claims 10.4%); within it, 59.1% of each forward block and 100% of
   each reverse block — the reverse direction carries no derivation at all, only a coordinate map
   and the obligation list.
3. **The rule instances** — every `Ref` is a positional index into a canonical order, and every
   generated coordinate/row lives at an offset the caller computes itself (test28: "layout
   S+k*m+e"; test23: "a hand-built mirror of the kernel's extension"; test19: observations
   addressed as `RowEq:1668+i`).

So the compiler-facing API should be a *typed builder plus a plan*, organised in four layers.
Everything in L1–L3 is additive: it emits the same RPA/RPX objects the wire format already
defines. A shorthand is only acceptable if it expands to the identical checked object
(test66 makes this point explicitly for projection shorthands: at `crates/core/src/point.rs`
a strictness claim *requires* a projection covering every coordinate on both sides).

### L1 — model and edit layer (source + edits → target + ledger)

```rust
let src: Model = Model::load("source.mcm")?;              // typed, streaming, exact
let led  = EditLedger::new(&[
    Edit::DeleteColumn { var: v, reason: Reason::ZeroByRow(r) },
    Edit::Substitute   { var: v, map: Affine::from_row(r, pivot, rhs) },
    Edit::DeleteRow    { row: r, witness: Witness::Combination(vec![(r2, q!(1)), (r3, q!(-1))]) },
    Edit::SetRowSense  { row: r, sense: Le },              // test50 flips 320 senses
    Edit::RelaxIntegrality { var: v },                     // test26/test50/test56
    Edit::FixValue     { var: v, value: q!(0) },           // test32/test16/test35
    Edit::AddRow       { row: RowSpec::new(...) },         // test19/test44/test49/test66/test86
]);
let (tgt, report) = led.apply(&src)?;                      // == the committed target.mcm
let audit = led.audit(&src, &tgt)?;                        // per-record receipts, not a hash
```

Why: test22 needed a range-aware readback (a `G` row's `RowUpper` is `rhs + range`, which the
prep-side helper got wrong and had to override); test31's agent asserted integer coefficients
and died on 349,755 rational objective coefficients, so readback must *type* each field and
offer streaming for 200 MB inputs; test47 lost a whole construction attempt to the text
container-depth cap (see L3 preflight).

### L2 — claim and obligation planning

```rust
let intent = Intent::PreserveOptimumAndProjection { program };     // or Equality / Level / Face
let plan   = plan(&src, &tgt, &led, intent)?;   // claim grid x obligations, machine-readable
plan.obligations[0]  // { claim: 0, kind: VarLower, site: Coord(17), discharge: Direct(RowEq(3)) }
plan.missing()       // properties the caller declared but no claim discharges  (test62's gap)
plan.preview()       // bytes / obligations / linear terms / peak live facts / json depth
```

- The plan — not the caller — must own the check list: it is the checker's own enumeration.
- Projection and observation forms need *derived* variants: `Projection::Identity(coords)`,
  `Projection::Pairs(..)`, `Projection::Derived { claim: u32 }`. This is the single largest
  mechanical waste in the corpus, measured on the shipped requests: test39 10,984,671 of
  10,985,003 bytes (99.997%), test66 3,029,919 of 3,030,310 (99.99%), test32 174,609 of
  174,941 (99.8%) — one identity list repeated once per claim, and in test66 the same list
  again as three 73,728-entry `Return` maps (54.1% of its RPA). test83's request is 24 MB for
  a 100-row model; test11, test43, test45, test56, test57, test65 are the same story at other
  scales.
- Claim scope must be explicit, not prose: test24's "optimality-preserving" claim excludes
  points, and that exclusion scope exists only in the README; test62's V7 receipt records
  `ancillary_point_contract.certified=false` for a property the report still stated, and the
  kernel could not see the gap because the request has no field for declared properties.

### L3 — rule builders, templates and preflight

```rust
let mut b = Builder::new(&src, &tgt, &plan, &mut budget);
let z = b.lin(Kind::Le, terms, q!(0))?;            // kind-checked, preconditions asserted
let e = b.eqpair(pos, neg)?;
let c = b.cases(Kind::Le, target_expr, split_var, |br| br.witness(...) /* , .. */ )?;
let scoped = b.generated_scope();                   // owns coordinate/row offsets (test28, test59)
let batch  = b.batch(&items, |b, item| b.rule_template(..));   // test31/test36/test42/test59/test66
let est    = b.preflight(&plan);                    // bytes, work, live facts, json depth, text cap
```

- The de-facto builder already exists twice in Python (`SparseBuilder` imported by 34
  generators, `Builder` by 32) and once more in the kernel's own tests — the same `lin` helper
  is copied into six test files (`crates/core/tests/{local_cases,menu_bijection,objective_level,
  signed_lift,adversarial_review,diagnostics}.rs`). Making one typed version public and
  precondition-checked replaces ~12,700 lines of generator support.
- Templates matter because the text cap binds: test36's certificate is 267,140,625 B against
  the unchanged 268,435,456 B limit (99.5%), test72's is 218 MB, test16's is 109.7 MB and is
  written *five times* (four 109.7 MB mutant copies plus the proof), test59 spends 110 MB of
  129 MB on 615,132 identical per-option steps, test62 emits 81,355 `Cases`, test42 emits
  383,586 steps for 166,500 deleted rows by sharing bisection facts. test66 computes where the
  wall is: its 20,484-instance cut family would hit the text cap at about 101,000 instances.
- Preflight must include the *container* depth, not only the logical one: `serde_json`'s
  nesting capacity is 128 and a deeper document is rejected as a resource outcome
  (`crates/core/src/rpa.rs`, `json_error`: "recursion limit exceeded at line …" →
  `RESOURCE_LIMIT`). test47's accepted certificate sits at json depth 126 with proof depth 38
  (`cases/test47/depth.json`), and the discarded linear-search version reached container depth
  186 — a case that lost real work to a limit nothing warned about.
- Failures should name the rule site, not just an index: test27's agent removed a premise and
  got "INVALID signed: exactly five premise references required" with no mention of the
  element; test40's mutation surfaced only as "INVALID obligation mismatch: expected Eq;
  obligation 854". The recent `location{claim,point,block,step,obligation}` addition is
  exactly the right channel; it needs to reach *builder-time* diagnostics too.

### L4 — verify, attack and reuse

```rust
let report = verify_claims(&src, &tgt, &proof, &request, &Limits::default())?;  // per claim
let bundle = verify_bundle(&manifest)?;          // test46: three parts, one contract
let attack = attack(&proof, Mutation::DropPremise { step, index })?;  // must be INVALID
let diff   = oracle::compare(&built_facts, &independent_model)?;      // the honest oracle
```

- 79 of 90 generators already build negative checks, 51 by deep-copying the certificate and
  mutating one premise; every case in `cases/*/preparation.json` records mutations that must be
  rejected (`INVALID`). That is the corpus's own TCB discipline and it should be an API call,
  not a per-case script: test18's analyst sketched `attack(cert, mutation) -> AttackReport
  {expected, got, code, location}`.
- test46 shows the multi-part case: three complete one-claim certificates, one merged RPA that
  cannot assemble inside the text cap, and a `bundle.json` that binds all three to one
  source/target pair. A `verify_bundle` that returns per-part status and one all-verified flag
  is the natural API; today `tools/check_delivery.py` re-implements it.
- Every trajectory wrote its own independent checker (`output/verify.py`, 160–209 lines in the
  cases read here) because a second implementation is the only evidence the corpus accepts.
  An oracle/compare route turns that from per-case work into one reusable check, and it is
  also how a builder can be validated before it is trusted.

### Suggested order (by demand, not by taste)

| phase | capabilities | why first |
|---|---|---|
| M1 | `MODEL_READBACK` + `EDIT_AUDIT`/`TARGET_CONSTRUCTION` + `CLAIM_PLANNING` + one `RULE_BUILDERS` core (`lin`/`round`/`eqpair`/`cases`) | removes the untrusted-edit and hand-written-obligation layer; every case needs the builder, and 73% need the edit record |
| M2 | `BATCH_TEMPLATES` + derived projections + `WORK_PREFLIGHT` | the text cap and the request bloat are today's binding constraints (test36/test72/test16/test59/test66) |
| M3 | `DIAGNOSTICS` at rule sites, `COUNTEREXAMPLE_TESTING`, `ORACLE_CHECKS`, `REUSE_LIBRARY`, `INCREMENTAL_VERIFY`/`MULTI_PART_ASSEMBLY` | turns per-case discipline into a checked, reusable workflow |

### What the API should *not* do

- Do not weaken a check to make a shorthand cheap: a derived projection must expand to the same
  complete coordinate list the verifier checks today (test66), and a strictness point must keep
  covering every coordinate (test34, test37, test44, test66).
- Do not put case-specific schemas in the kernel: test37's hint keys, test29's
  `exact-support-class-reformulation-1`, test20's `aggregate_balance_certificates` — those are
  the *compiler's* vocabulary; the kernel's edit vocabulary should stay small and general.
- Do not require a solver, a heuristic or a global bound anywhere: every capability above is
  exact-rational bookkeeping, and the corpus's claims are all of the form "this relation holds
  for all points of the declared domain", not "this is a better model".

```sh
  --out-dir /tmp/api-demand-tables
```

## 8. Limitations of this analysis

- The trajectories are the **solver-blind baseline** runs (`runs/<case>-nomf-B1/`). They show
  what a competent analyst needed, not what a solver-assisted analysis would need; no claim
  here depends on a solver.
- Each `api_needs[].sketch` is a design proposal made by one analyst reading one case; the
  synthesis in §5 is the author's, and where a proposal would change the *wire format* it is
  called out as needing expansion into today's checked objects rather than as a new encoding.
- Capability counts weight cases equally, so a capability raised only by large cases (for
  example `WORK_PREFLIGHT`) is understated relative to the bytes it would save.
- The corpus is fixed at 81 accepted cases; demand for capabilities that only *rejected*
  reformulations would need (for example a way to prove "no improvement exists") is not
  measured here.
- Numbers quoted from case artifacts (work, obligations, bytes, line counts) were read from
  `cases/*/preparation.json`, `cases/*/README.md` and the artifact files themselves; where an
  analyst's figure disagreed with the artifact, the artifact was used.
